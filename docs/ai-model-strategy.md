# AI 모델·API 전략 — 항목별 라우팅 + 효율/품질 비교 설계

> "API를 항목별로 다르게 쓰면 퀄리티가 낫지 않을까? 예술은 시각적·감성적이라 퀄리티가 중요"라는 문제의식에 답하는 문서.
> **결론을 못박지 않는다** — 항목별 라우팅 **잠정 권고** + 실제로 돌려서 고를 수 있는 **비교 harness 설계**를 제시한다.

## 1. 현 상태 진단 — 레포 모델은 레거시

- `lib/gemini.ts`는 **`gemini-1.5-flash` 단일 모델**을 모든 용도에 쓴다. Flash는 속도·단가 최적화 모델이지 **설득
  카피·시각 추론 최강**이 아니다. 감성·고설득 콘텐츠에선 품질을 손해 본다.
- **2026 라인업 현실**(아래 §2): 1.5 세대는 레거시. 현 기본은 **Gemini 3.5 Flash**, 멀티모달/고난도 최강은 **3.1 Pro**,
  대량 저가는 **3.1 Flash-Lite**.
- **SDK 주의**: 레포는 `@google/generative-ai`(구 SDK) 0.24.1. 신모델·`thinking_level`·`responseSchema` 활용은
  통합 **Gen AI SDK(`@google/genai`)** 로의 마이그레이션이 필요할 수 있다 → 모델 갱신 시 **반드시 SDK 호환 검증**.

## 2. 모델 후보 & 항목별 라우팅 매트릭스 (잠정 권고)

### 2.1 후보군

| 모델 | 강점 | 단가(대략, 1M tok) | 적합 용도 |
|---|---|---|---|
| **Gemini 3.1 Pro** | 멀티모달·고난도 추론 최강(Video-MME 선두), 2M 컨텍스트 | 입력 $2~4 / 출력 高 | 비전 분석·고설득 카피 |
| **Gemini 3.5 Flash** | 균형(품질↑·속도·`thinking_level`로 조절) — 현 기본 | ~$1.5 입력 / $9 출력 | 대부분의 카피 |
| **Gemini 3.1 Flash-Lite** | 최저가·대량 | ~$0.25 입력 | 짧고 저난도(단골 메시지) |
| **(옵션) 크로스-프로바이더** | 감성·hero 카피 품질 비교용 | 별도 | A/B 후보로만 |

> 단가는 시점·리전에 따라 변동 → harness 실행 시 실측가로 갱신. ([Pricing May 2026](https://www.metacto.com/blogs/the-true-cost-of-google-gemini-a-guide-to-api-pricing-and-integration))

### 2.2 라우팅 매트릭스 (출발점 — harness로 검증 후 확정)

| 단계/콘텐츠 | 난도·특성 | **잠정 모델** | 근거 |
|---|---|---|---|
| **Stage1 비전**(작품 분석) | 시각 정확도·환각 최소가 생명 | **3.1 Pro** | 멀티모달 최강, art 품질의 출발점 |
| `landing_detail` 상세페이지 | 고설득·구조·임팩트 | **3.1 Pro** (vs 3.5 Flash A/B) | 전환 직결, 품질 우선 |
| `ad_copy` 광고 카피 | 첫 줄 임팩트·미세 튜닝 | **3.1 Pro** (vs 3.5 Flash A/B) | 광고비 효율 직결 |
| `instagram_caption` | 감성·짧음·양 많음 | **3.5 Flash** (+thinking_level) | 균형·빈도 높음 |
| `naver_blog` | 장문·구조·SEO | **3.5 Flash** (high thinking) | 길이·구조 안정 |
| `smartstore_detail` | 구획·스펙→이득 | **3.5 Flash** | 정형성 높음 |
| `customer_message` | 짧음·저난도·대량 | **3.1 Flash-Lite** | 단가 최적, 품질 충분 |

**원칙**: **돈/전환이 걸린 곳에만 Pro**, 양이 많고 정형적인 곳은 Flash, 짧고 저난도는 Flash-Lite. `thinking_level`
(minimal~high)로 같은 모델 안에서도 품질/비용/지연을 콘텐츠별로 조절.

### 2.3 크로스-프로바이더는 "검증 후 결정"

감성·hero 카피(상세/광고)에서 타 프로바이더가 유의미하게 낫다면 **그 항목만** 다른 API로 라우팅할 수 있다. 단
**운영 복잡도(키 관리·SDK·장애 격리·비용 추적)** 가 늘므로, **harness 비교에서 품질 우위가 명확할 때만** 채택. 기본은
Gemini 단일 프로바이더 + 티어 라우팅.

## 3. 효율/품질 비교 Harness 설계 (실행 가능)

"효율 비교를 해야 한다"는 요구를 **실측 가능한 절차**로 구체화. (실행은 API 키·테스트 이미지 필요 → 후속 작업)

### 3.1 고정 테스트셋
- **작품 사진 N=20~30장** × 카테고리 7종 골고루(도자기·레진·회화·캘리·유리·한지·기타).
- 각 사진에 **작가 페르소나 2종**(예: A2 전업·전환형, A1 고령 장인형) 매칭 → 입력 케이스 행렬.
- 케이스는 고정·버전관리(재현성). 정답이 아닌 **기준 입력**.

### 3.2 비교 축(셀)
- 행 = 콘텐츠 5종(+비전), 열 = 후보 모델(3.1 Pro / 3.5 Flash / Flash-Lite / 옵션 크로스).
- 비전 단계는 별도(시각 브리프 정확도 단독 평가).

### 3.3 채점 루브릭 (= copywriting-engine §9와 동일, 단일 소스)
각 출력에 0~2점:
1. 사실→이득 변환 2. 감정/시각화 3. 채널 규격 준수 4. **환각 없음** 5. 과장/효능/최상급 없음 6. CTA 명확 7. 브랜드 톤
8. (단골) 컴플라이언스 + **한국어 자연스러움**(별도 축).
- 비용: **생성당 토큰·원가**. 지연: **응답 시간(p50/p95)**.

### 3.4 채점 방식
- **1차: LLM-judge**(강모델로 루브릭 자동 채점) — 빠른 스크리닝.
- **2차: 사람 검수**(상세/광고 등 고가치 항목은 사람이 최종) — judge 편향 보정.
- 환각 항목은 **사진 대조 사람 확인**(가장 중요).

### 3.5 결과표 템플릿 (채워서 의사결정)

| 콘텐츠 | 모델 | 품질(0~16) | 한국어 | 환각율 | 생성단가 | 지연 p95 | 채택? |
|---|---|---|---|---|---|---|---|
| landing_detail | 3.1 Pro | | | | | | |
| landing_detail | 3.5 Flash | | | | | | |
| instagram_caption | 3.5 Flash | | | | | | |
| customer_message | Flash-Lite | | | | | | |
| (vision) | 3.1 Pro | | | | | | |
| … | | | | | | | |

**의사결정 규칙**: 품질 동률이면 **싼·빠른 쪽**. Pro가 Flash 대비 품질 우위 < 임계치면 Flash로 다운그레이드(단가↓).

## 4. 단가 / 유닛 이코노믹스

- 생성당 토큰 비용 = (입력: 시스템 프롬프트+시각브리프+few-shot) + (출력: 콘텐츠) × 단가.
- **비전 단계(Pro)가 가장 비싼 구간** → 같은 작품으로 5종을 만들 땐 **시각 브리프 1회 생성 후 캐시·재사용**(브리프를
  `marketing_contents.meta.vision_brief_id`로 공유)해 비용을 분산.
- Pro는 전환 직결 항목(상세·광고)에만 → 평균 생성 단가를 낮게 유지. 이 단가가 SaaS 요금·마진의 입력값.

## 5. 권고 결론 (출발점, 확정 아님)

1. **레포 모델 갱신**: `gemini-1.5-flash` → 기본 **3.5 Flash**. (SDK 호환 검증 후)
2. **항목별 라우팅 도입**: 비전·고설득(상세/광고) = **3.1 Pro**, 일반 카피 = **3.5 Flash**, 단골 = **Flash-Lite**.
3. **`lib/gemini.ts`를 모델 라우터로 확장**: `getModelFor(kind, stage)` 형태로 콘텐츠·단계별 모델/`thinking_level` 반환.
4. **harness(§3) 실행으로 검증·확정**, 크로스-프로바이더는 명확한 우위가 있을 때만.
5. 시각 브리프 **1회 생성·재사용**으로 비용 최적화.

> 모든 수치(단가·벤치)는 시점 의존 → 구현 직전 실측으로 갱신. 본 문서는 **선택의 틀**이지 고정된 답이 아니다.

## 6. 매칭/큐레이션용 임베딩 (소비자 발견 면 — Phase 1~2, ★조기 우선)

소비자 우선 전략이므로 매칭/큐레이션은 **초기부터** 핵심이다(Phase 1 매칭 v1 → Phase 2 임베딩 심화 —
[`curation-matching.md`](./curation-matching.md) §6). 큐레이션("내가 찾던 예술")은 **생성(LLM)과 다른 비용·기술 축**이라 별도 관리한다.

- **목적**: 소비자 취향 프로파일 ↔ 작품을 **유사도**로 매칭([`curation-matching.md`](./curation-matching.md) §4).
- **방식(하이브리드)**:
  1. **규칙 기반** — 공유 매칭 속성([`curation-matching.md`](./curation-matching.md) §3: style·mood·color·price_tier·occasion·region·values)
     일치 가중. 시각 브리프에서 자동 채워지므로 **추가 비용 ≈ 0**(생성 시 부산물).
  2. **임베딩 유사도** — 작품(이미지+카피)과 취향(입력+행동)을 벡터화해 의미적 매칭. 미묘한 "취향"을 잡는다.
- **임베딩 후보**: 텍스트 임베딩(저단가·범용) vs **멀티모달 임베딩**(작품 이미지 직접 — art에 유리). 후보·단가는 harness로 비교.
- **저장/검색**: **pgvector**(Supabase Postgres 확장)로 작품 벡터 인덱싱 → ANN 검색. 별도 벡터 DB 불필요(운영 단순).
- **라우팅 매트릭스 추가 행**:

| 단계 | 특성 | 잠정 선택 | 근거 |
|---|---|---|---|
| 매칭 인덱싱(작품 임베딩) | 작품당 1회·배치 | 멀티모달 or 텍스트 임베딩(비교) | art는 시각 의미가 핵심 → 멀티모달 우위 가능 |
| 취향 쿼리(소비자) | 실시간·빈번 | 동일 임베딩 공간 | 인덱스와 같은 공간이어야 매칭 |

- **비용 메모**: 임베딩은 생성 LLM보다 훨씬 저렴하고 작품당 1회(갱신 시만 재계산) → 큐레이션 단가는 낮게 유지. Pro 라우팅(생성)과 분리해 관리.
- **콜드스타트**: 소비자 경험을 day-1부터 풍부하게 하려면 시드 공급이 필요 → **작가 플로우 최소화(컨시어지/AI 대행)** 로 작품 인덱스를 채운다([`curation-matching.md`](./curation-matching.md) §5·§6).
